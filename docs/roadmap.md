## Chantiers structurants

### R1 — Loi de statut du worker ✅ (condition de R2 satisfaite)

**Résultat** : loi pure `workerStatusLaw.ts`, transitions exhaustives, événements câblés au repository, saga, plugins et bridge realtime ; migration IndexedDB v31 → v32 ; tables de présentation UI exhaustives. Le timeout `POSTING` de stratégie 2 est fixé à 60 secondes.
**Critère de sortie satisfait** : hors module et tests, les comparaisons/mappings worker passent par des prédicats ou les tables exhaustives de présentation ; les écritures brutes de statut sont limitées à la création/migration et à la transaction du repository ; le type de `patch()` exclut `status` et `queue`, avec assertion de type dédiée.
**Vérification** : table de transitions autorisées/refusées, repository et migration v31 → v32 couverts par tests ciblés. Les flows et décisions métier sont documentés dans [statuts.md](./statuts.md). La galerie garde le verrou scope collection (D-008/D3) ; chaque enum a sa table UI `Record` exhaustive sans `default` (D-008/D5).

### R2 — Moteur de file headless, puis retraite de Redux-Saga (candidate 4, D-006)

R1 étant terminé, le prérequis est satisfait : extraire de `sagas/workers.ts` un `queueEngine.run(worker, plugin, ports)` (ports : repository, horloge injectée pour l'EMA, notifieur) ; saga, `useJobRealtime` et récupération au démarrage deviennent des adaptateurs fins. Corriger au passage la fuite d'attente du stop-listener (l'attente en cours n'est pas annulée à l'arrêt). La loi de statut centralisée est celle qu'appliquera le moteur.

### R3 — Repositories sur le vrai stack (D-004)

1. ✅ Harnais `createTestDb()` avec `fake-indexeddb` : réinitialise la base Dexie réelle entre les tests ; à généraliser aux autres repositories au fur et à mesure de leur couverture.
2. `deleteByScope` retourne réellement les ids calculés (test d'abord, y compris le chemin `startsWithIgnoreCase` du scope collection).
3. ✅ `updateTaskStatus` applique la transition, la file et le statut dérivé du worker dans une transaction unique (livré avec R1).
4. Aligner la signature `WorkerRepository.add` (`WorkerCreateDTO → Promise<Worker>`).
5. `deleteByScopeAndType` : décider d'implémenter ou supprimer le paramètre fantôme `isTemp` (grep des call sites d'abord).
6. Les 2 imports `@/App` depuis `src/data/**` supprimés (violations de couches réelles, cf. Q4).

### R4 — Worker LLM unifié derrière une interface de découplage `LLMClient` (candidate 3)

`mistral.ts` et `openai.ts` sont quasi identiques hors construction du client (~200 lignes dupliquées ; la copie OpenAI écrit même des fichiers `mistral_export_*`) ; Mistral contourne l'interface de découplage existante avec son SDK. Cible : un worker d'extraction paramétré par adaptateur (adaptateur Mistral, adaptateur compatible OpenAI), flux d'export JSON/CSV/XLSX écrit une seule fois (la triplication de `mistralOcr.ts` converge aussi).

### R5 — Module `Attachments` (candidate 5)

Donner un foyer au concept « blob + sa forme base64 » (~40 lignes dupliquées dans ~15 fichiers, cinq types d'adaptateurs sans module pour les encapsuler, deux mécanismes de miniature différents portant le même nom). Interface cible : `put / get / remove / asBase64 / fromBase64` derrière l'agrégat Sources ; import/export sérialisent les attachments comme une unité.

### R6 — `useDialog` : une interface de découplage `openForm` (candidate 6)

`hooks/ui/useDialog.tsx` : 447 lignes, 23 méthodes wrapper, ~43 sites d'import, point chaud du dépôt. Cible : un registre de formulaires + `result = await openForm(name, props)` qui absorbe allocation de ref, `requestSubmit`, close-on-action, titres i18n.

### R7 — Restructuration feature-first (D-009) ✅

**Cible** : `src/components/{ui,common,layout,features/<domaine>}` (D-009). Pas de déplacement global : migrer par tranches cohérentes, à l'occasion d'un changement fonctionnel, et conserver les chemins existants tant qu'un déplacement n'apporte pas de valeur nette.

**Plan d'exécution**

1. **Poser les frontières** : `ui/` pour les primitives génériques (notamment shadcn, sans logique métier) ; `common/` uniquement pour les composants applicatifs réutilisés par plusieurs domaines ; `layout/` pour le shell et la navigation transversale ; `features/<domaine>/` pour l'UI métier et ses styles/tests propres. Pages, hooks, modèles et accès aux données restent dans leurs couches actuelles. Éviter les composants « communs » prématurés et les dépendances d'une feature vers une autre.
2. **Continuer la règle d'atterrissage** : tout nouveau composant métier va directement dans `features/<domaine>/`; les nouvelles primitives UI vont dans `ui/`. Garder les tests et styles co-localisés lorsque possible.
3. **Piloter sur workers** : première tranche appliquée — `WorkerLabel`, `WorkerStatusIcon`, `WorkerDetails`, `WorkerDataTable` et `WorkerTable` rejoignent `features/workers/` avec `statusPresentation.tsx` ; leurs consommateurs pointent vers les nouveaux chemins. Aucun déplacement des pages, hooks ou contextes. TSC et tests ciblés worker passent ; poursuivre l'approche opportuniste pour les composants non concernés par cette tranche.
4. **Étendre par opportunité** : deuxième tranche appliquée à `features/collectionInspector/` : l'écran, sa galerie, ses actions, ses compteurs et ses composants de vignette sont regroupés ; la page importe désormais l'écran depuis cette feature. Troisième tranche appliquée à `features/manifests/` : galerie, navigation et présentation des manifests, avec leurs composants auxiliaires et leur CSS ; seule `ManifestExplorerPage` consomme cette feature. Quatrième tranche appliquée à `features/modifiers/` : flux, nœuds, formulaire, dashboard et styles sont regroupés ; les pages et le canvas viewer pointent vers cette feature. Cinquième tranche appliquée à `features/canvasViewer/` : visualiseur et navigation de canvas sont regroupés ; pages, inspecteur de collection et `QuickCanvasViewer` utilisent les nouveaux chemins. Sixième tranche appliquée à `features/models/` : dashboard, éditeur, liste d'usages, aperçu et sélecteur de couleur regroupés ; la page modèles et le hook de dialogue utilisent les nouveaux chemins. Septième tranche appliquée à `features/configuration/` : les trois onglets sont regroupés et la page de configuration utilise les nouveaux chemins. Huitième tranche appliquée à `features/storage/` : les vues de stockage local et IIIF ainsi que leur carte de manifest sont regroupées ; les pages utilisent les nouveaux chemins. Neuvième tranche appliquée à `features/collections/` : gestion de collections, pagination et indicateurs OCR/LLM sont regroupés ; la page de gestion et l'inspecteur utilisent les nouveaux chemins. Dixième tranche appliquée à `features/projects/` : sections de sélection de projet et de sources du workflow de démarrage regroupées, sans déplacer la page ni la logique de données. Onzième tranche appliquée à `common/` : formulaires pilotés par le registre central de dialogues, menus partagés et panneaux de journalisation sont regroupés comme infrastructure transversale ; les primitives restent dans `ui/`. Douzième tranche : les composants applicatifs réellement transversaux (dont boutons à infobulle, indicateurs génériques, barre d'outils et états vides/chargement) sont regroupés sous `common/`; le menu workers reste sous `features/workers/`. `QuickCanvasViewer`, `DocSideBar` et `ExpertReportCard` rejoignent respectivement `features/canvasViewer/`, `features/documentation/` et `features/expert/`. La barre latérale applicative rejoint `layout/`. Les pages et consommateurs utilisent les nouveaux chemins. Ne pas ouvrir de tranche dédiée uniquement au rangement des composants qui restent à la racine ; ne pas déplacer les pages/hooks/services pour satisfaire l'arborescence.
5. **Contrôler chaque tranche** : rechercher les imports entrants avant un déplacement ; vérifier alias, imports circulaires et dépendances entre couches ; exécuter les tests ciblés, puis types et build si la tranche touche plusieurs domaines. Mettre à jour cette roadmap si une frontière se révèle inadéquate.
6. **Faire un bilan avant d'élargir** : les domaines migrés restent lisibles, sans wrappers ni barrels ajoutés ; les imports inter-features restent des usages directs de composants métier partagés. Le déplacement du canvas viewer rapproche `CollectionNavigation` de son unique consommateur. `common/` distingue désormais ses formulaires, menus et logger, tandis que les composants métier/documentation/expertise sont dans leur feature et la navigation transversale dans `layout/`. Les primitives restent dans `ui/`; pages, hooks, services, modèles et contextes ne sont pas déplacés. Les composants racine restants ne justifient pas de migration mécanique supplémentaire.

**État et bilan final (2026-10-12)** : migration opportuniste réalisée pour les domaines workers, collection inspector, manifests, modifiers, canvas viewer, models, configuration, storage, collections, projects, documentation et expert, ainsi que pour les composants transversaux et la navigation. `common/` regroupe les composants applicatifs transversaux, leurs formulaires, menus et panneaux de journalisation ; `layout/` contient la navigation transversale ; `ui/` conserve les primitives ; les composants métier sont classés dans `features/<domaine>/`. Pages, hooks, services, modèles et contextes restent dans leurs couches dédiées. Les dossiers historiques encore présents sont vides ou contiennent des éléments techniques à conserver. Aucun barrel/wrapper n'a été introduit et aucun déplacement mécanique supplémentaire n'est justifié.

**Validation finale** : `npx tsc --noEmit -p tsconfig.app.json` passe ; Vitest : 98 tests réussis, 1 ignoré et 1 todo ; `git diff --check` passe. Prettier signale des écarts de formatage dans 24 fichiers du périmètre ; ils n'ont pas été corrigés afin de ne pas mêler du reformatage à cette migration structurelle.

**Critères de sortie** : les nouvelles contributions respectent les frontières ci-dessus ; les domaines migrés sont autonomes et leurs imports/tests/styles suivent les déplacements ; aucun grand déplacement sans changement fonctionnel associé ; les exceptions restantes sont intentionnelles et documentées. Pas de règle de lint d'architecture dédiée à R7 tant que les frontières ne sont pas éprouvées (voir Q4).

## Comment reprendre un chantier

1. Lire ce fichier, l'ADR citée par le chantier, et `CONTEXT.md` (vocabulaire).
2. Commandes de vérification CI : `npx tsc -b && npx vitest run && npm run lint:ratchet && npx prettier . --check` ; ajouter les E2E pour les parcours concernés.
3. Respecter la proportionnalité (D-004) : pas de nouvelle abstraction sans besoin au call site ; les commits sont petits, un commit par port/famille.
